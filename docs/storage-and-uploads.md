# TradeNest Storage — Managed uploads (S3-compatible, no stack changes)

## Scope and locked invariants

This pass builds upon Api contracts without replacing Next.js 16, NestJS, PostgreSQL 18, Prisma 7, Zod 4, or the modular monolith. Storage is a shared infrastructure module (`apps/api/src/common/storage`), not an independent business microservice. The 74 blueprint endpoints remain; three explicitly checked extensions were added:

- `POST /api/v1/products/:id/images/upload-url` (SELLER, owner + active account policy)
- `POST /api/v1/disputes/:id/evidence/upload-url` (BUYER/SELLER dispute participant, OPEN dispute)
- `GET /api/v1/products/:id/images/:imageId/file` (public only for ACTIVE products)

The blueprint's original `POST /products/:id/images` and `POST /disputes/:id/evidence` still register metadata. They now reject arbitrary storage object keys and require actual S3 objects uploaded by the authorized owner. Browser-supplied `url` fields, if sent by older clients, are ignored. Product URLs are generated by the API; evidence metadata is stored with a private placeholder and replaced by two-minute signed download URLs only after `GET /disputes/:id` participant/Admin authorization. No signed S3 keys/credentials are stored in Prisma.

## Required deployment setup

1. Create a **private** S3-compatible bucket, e.g., `tradenest-uploads` in production or `tradenest-uploads-test` for local tests; do not configure public reads. Ensure automatic deletion of incomplete/unregistered `products/*` and `disputes/*` uploads through an object lifecycle policy (for example, 1 day). Use bucket encryption at rest and restrictive IAM policy.
2. Configure `STORAGE_S3_BUCKET`, `STORAGE_S3_REGION`, optional `STORAGE_S3_ENDPOINT`, and optionally explicit `STORAGE_S3_ACCESS_KEY_ID`/`STORAGE_S3_SECRET_ACCESS_KEY` (omitting both uses standard AWS credential resolution, e.g. task roles). Do not commit credentials. Deployment Compose now forwards these variables into NestJS.
3. The S3 endpoint embedded in the presigned URL must be accessible both to NestJS **and to the user's browser**. In production the endpoint must use HTTPS. With a locally launched API and MinIO container the endpoint can be `http://127.0.0.1:9000`.
4. Configure **bucket CORS** for the web app origin(s): allowed method `PUT`, allowed header `Content-Type`, and appropriate restricted origins (such as `http://localhost:3000` during local development). S3 authentication uses pre-signed URLs; never give browser access keys. CORS is an S3 bucket configuration, not a NestJS setting.
5. With Node 24 and pnpm 10.15.1, generate/review the real `pnpm-lock.yaml` using `pnpm install --lockfile-only` in registry-connected environment, then use `pnpm install --frozen-lockfile`. A genuine reviewed lockfile is required; source checks are not live acceptance.
6. Review and apply additive migration `202610080005_managed_upload_object_uniqueness` **after identifying/removing any preexisting duplicate object keys**. The original four migration files and the Database integrity manifest remain unchanged.

## User flow

1. Authenticated seller/buyer selects JPEG/PNG/WebP (5 MB) or dispute PDF (10 MB).
2. Next.js calls the NestJS upload-url command through its authenticated BFF API route; NestJS checks role, resource ownership/participation, and dispute status where applicable.
3. NestJS creates an unguessable object key tied to `kind/resourceId/userId`, with a five-minute PUT URL, fixed MIME, and no exposed S3 credentials.
4. The browser uploads bytes directly to S3 via HTTPS PUT, then calls the **existing** metadata registration endpoint with the object key.
5. NestJS validates the key/owner, HEAD object presence, 30-minute freshness, MIME, maximum size, and content magic bytes before storing the metadata. Duplicate object registration is constrained by PostgreSQL unique indexes.
6. Active-product images are served through a Next.js -> NestJS read-only binary proxy with `nosniff`; private evidence downloads are time-limited 120-second S3 signed links, only obtainable by dispute participants/Admin.

## Acceptance and verification

Run source checks independent of npm or running services:

```sh
node scripts/verify-storage.mjs
node --test scripts/tests/storage-guards.test.mjs
node scripts/verify-api-contracts.mjs
node scripts/verify-database-migration-chain.mjs
node scripts/verify-architecture.mjs
```

Runtime acceptance requires **all prerequisite acceptance suites**, clean migrations, a LOCAL isolated PostgreSQL test database, and a dedicated S3-compatible bucket whose name ends `-test`, reachable through a localhost S3 endpoint. Configure `STORAGE_S3_*` environment variables; do not use production credentials. Then run:

```sh
pnpm acceptance:storage
```

The protected storage smoke test (`pnpm --filter @tradenest/api verify:storage:storage`) exercises presigned PUT, HEAD, byte signature check, public-object read, private signed GET, and policy-denied keys; it deletes only the test objects it created. The Storage runner also executes Api contracts and frontend E2E regressions. A passed **static** check is not a runtime pass.

## Known hardening still required

- Actual MinIO/AWS S3 integration and browser CORS verification have not been run in this sandbox; the locked toolchain and real bucket are unavailable here.
- Actual content scanning (antivirus/malware scanning), object versioning/immutability, orphan cleanup policy deployment, and uploaded-file abuse rate limits must be considered before live production release. Magic-byte checks alone are not an antivirus.
- Existing metadata-only image/evidence records made before Storage may require validated re-upload; never promote arbitrary historical URLs to verified storage objects.
- Deployment validation must ensure live storage configuration is present before launch (Operations). Production payment provider and other roadmap passes remain incomplete.
